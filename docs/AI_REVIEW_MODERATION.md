# AI 리뷰 검수 구현 및 적용 체크리스트

## 선택한 API

- 제공자: 포텐스닷
- 요청 모델: `claude-5-sonnet` (사용자 지정)
- 엔드포인트: `POST https://ai.potens.ai/api/chat`
- 인증: 서버에서만 `Authorization: Bearer <POTENS_API_KEY>` 전송
- 요청: `{ "prompt": "검수 지침과 리뷰", "model": "claude-5-sonnet" }`
- 응답의 `message`를 `{ "decision": "pass|revise|uncertain", "categories": [] }`로 파싱하고 서버에서 재검증

짧은 분류 작업에는 소형 모델로도 시작할 수 있으나, 이번 구현은 요청받은 Sonnet 모델을 사용한다. 완성된 판정이 필요하므로 비스트리밍 API를 사용한다. 모델 변경은 서버 환경 변수로만 한다. 장애 시 다른 모델로 자동 전환하지 않는다.

## 검수 범위

| 코드 | 수정 요청 | 허용 또는 문맥 확인 |
|---|---|---|
| `profanity` | 욕설, 초성·기호 등 변형 욕설 | 부정적 평가, 불만, 낮은 별점 |
| `sexual` | 노골적인 성적 발언, 성희롱, 성적 만남 요구 | 중립적인 건강·교육·기능 설명 |
| `phone` | 휴대전화 번호, 한글 숫자·기호로 우회한 번호 | 주문번호·오류코드 등 |
| `external_solicitation` | 외부 가입·방문·구매·연락 유도 | 오류 경로·테스트 URL의 단순 설명 |

리뷰의 정성, 길이, 유용성, 별점, 긍정·부정 자체는 차단 사유가 아니다. 길이 제한은 API 처리량 제한이며 내용 평가 기준이 아니다.

제작자는 기존 프로필 영역에 SNS·블로그를 공개할 수 있다. 리뷰 안의 “내 SNS로 연락하세요”는 예외로 허용하지 않는다. 좋은 목적의 개별 제안은 제작자가 공개한 SNS의 DM을 이용하도록 안내한다.

대상은 리뷰 `answers`의 본문·문항별 답변과 그 안의 텍스트다. 별점, 계정 식별자, 퀴즈 정답, 증빙 스크린샷은 AI에 전송하지 않는다. 첨부 이미지/OCR/QR, 제작자 답글, 기존 리뷰 소급 검수는 이번 범위에 포함되지 않는다. 화면에서도 이미지 검수 제외를 명시했다.

## 처리 흐름

1. 브라우저는 `moderate-review` Edge Function만 호출한다.
2. 함수가 Supabase Auth로 사용자 JWT를 검증한다. 클라이언트가 보낸 사용자 ID·보상·승인 여부는 사용하지 않는다.
3. 서버에서 payload를 정규화하고 분량·형식을 검사한다.
4. 서버 전용 `begin_review_moderation` RPC가 실제 참여 자격과 사용자별 제한(분당 5회, 하루 50회)을 확인한다. 분산 호출에도 DB 잠금으로 제한한다.
5. 명확한 휴대전화 번호는 외부 전송 전에 수정 요청한다. 나머지는 포텐스닷으로 분류한다. 외부 링크를 직접 열지 않는다.
6. 결과는 비공개 테이블에 정책 버전·모델·분류 코드·본문 해시로 기록한다. 원문, 전화번호, API 원응답은 검수 로그에 저장하지 않는다.
7. 통과한 경우 사용자 세션으로 기존 `submit_project_review`의 새 승인 확인 경로를 호출한다.
8. DB가 사용자·프로젝트·전체 payload의 SHA-256·정책 버전·5분 유효기간을 확인한 뒤 기존 저장 및 코인 지급 트랜잭션을 실행한다.

검수 상태는 제작자 승인 상태와 분리되어 있다. 기존 리뷰 리워드와 최초 게이팅 보너스는 유지한다. 기존의 검수 없는 제출 함수는 비공개 스키마로 이동하고 직접 실행 권한을 제거한다. 승인된 내용을 수정하거나 승인 없이 INSERT 하는 경로도 차단한다. 동일 승인 재요청에는 기존 결과를 반환하며 추가 코인을 지급하지 않는다.

거절·판단 보류·25초 시간 초과·공급자 장애·형식 오류는 모두 저장/지급을 진행하지 않는다. 입력은 작성 화면에 유지되고 버튼이 다시 활성화된다. 판단 보류는 운영자 대기열에 자동 등록되는 기능이 아니며, 화면에 수정·재시도 또는 고객센터 문의를 안내한다. 검수번호로 비공개 판정 기록을 찾을 수 있다.

## 적용 순서 — Supabase 관리자 권한 필요

DB 소유자 계정으로 CLI 인증을 완료했다. 운영에는 일부 과거 변경이 이력 없이 적용돼 있고 프로젝트 검증 컬럼과 서버 퀴즈 채점은 누락돼 있었다. 과거 마이그레이션 일괄 재실행은 피하고 새 보완 마이그레이션으로 필요한 구조만 복구한다. 기존 지급 함수와 500코인 최초 보너스는 유지하며, 이미 적용된 SQL 파일은 변경하지 않는다.

1. `creator-web`에서 Supabase CLI에 로그인하고 대상 프로젝트를 확인한다.
2. 로컬 비밀 파일을 Supabase 함수 비밀값으로 등록한다. 키를 명령 인자에 직접 적지 않는다.

   ```powershell
   supabase secrets set --env-file supabase/functions/.env.local --project-ref <프로젝트_ID>
   ```

3. 함수를 먼저 배포한다. 이 단계에서 새 프런트엔드를 공개하지 않는다.

   ```powershell
   supabase functions deploy moderate-review --project-ref <프로젝트_ID>
   ```

   `config.toml`에서 플랫폼의 레거시 JWT 검사를 끄고 함수 내부의 `auth.getUser()`로 검증한다. 인증되지 않은 요청은 AI 호출·DB 작업 전에 거부한다.

4. `node scripts/prepare-review-release.mjs`로 이번 배포 4건을 묶은 SQL을 만든다. `supabase/.temp/review-release-rehearsal.sql`은 시험 후 항상 롤백하며, `review-release.sql`은 변경과 마이그레이션 이력을 한 트랜잭션으로 커밋한다. 이 스크립트는 이번 릴리스 전용으로, 이미 적용된 버전을 발견하면 중단한다. 운영 이력 차이 때문에 `db push --include-all`로 과거 SQL을 재실행하지 않는다. 이전 프런트엔드는 승인 ID가 없어 제출할 수 없으므로 DB와 프런트엔드 전환을 함께 진행한다.
5. 새 프런트엔드를 배포한 뒤 아래 확인을 완료한다.
   - 정상 리뷰: 리뷰 한 건, 보상 한 건, 참여 완료
   - 위반 리뷰: 수정 안내, 입력 유지, 리뷰·보상 없음
   - API 장애: 재시도 안내, 리뷰·보상 없음
   - 낮은 별점, 제작자 프로필의 SNS·블로그, 기존 퀴즈/스크린샷 검증 유지
   - 직접 RPC·본문 변경·다른 사용자 승인 재사용 실패
6. 문제가 생기면 리뷰 제출을 일시 중지하고 원인을 수정한다. 검수를 생략하는 자동 통과나 이전 RPC 우회는 사용하지 않는다.

## 로컬 재검증

```powershell
cd creator-web
npm test
npm run build
```

가상 사례만 외부 API에 전송하는 유료 호출 확인은 별도 명령으로 실행한다. 일반 테스트는 네트워크나 실제 키를 사용하지 않는다.

```powershell
node scripts/check-review-provider.mjs
```

운영에서는 오탐 문의, 판정별 비율, 지연, 공급자 사용량을 확인한다. 비공개 검수 기록의 보관 기간과 정리 주기는 운영 정책으로 확정해야 한다. 리뷰 원문을 분석 도구나 일반 로그에 추가하지 않는다.
