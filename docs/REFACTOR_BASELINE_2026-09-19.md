**1단계 전체 완료로 간주하지 않는다.** 테스트 통과와 HTTP 200은 브라우저의 렌더링·로그인·저장·교환 성공을 의미하지 않는다. 읽기 흐름은 12절에서 보충했지만, **등록·참여·후기·교환·문의처럼 서버 상태를 바꾸는 흐름은 아직 한 번도 실행하지 않았다.** 이 흐름에는 테스트 3회를 완료한 계정과 쓰기가 허용된 테스트 데이터가 필요하며, 그것을 확보해 B07–B11·B14를 기록한 뒤에 구조 변경의 기준선으로 확정한다.

최초 브라우저 도구는 현재 URL을 확인하지 못해 UI 조작을 중단했다. 이후 사용자가 Chrome 확장 프로그램을 연결했고, **같은 날 재확인에서 연결 및 페이지 조작이 정상 동작했다.** 최초 중단은 앱 자체 오류가 아니었으며 현재는 해소됐다. 1차 재확인 결과는 10·11절, 로그인 계정으로 이어서 진행한 2차 확인 결과는 12절, 그 과정에서 관찰한 기존 동작 문제는 13절에 기록한다.

## 6. 상태·초기화·분리 주의사항

1. **같은 이름의 함수가 두 번 선언됨.** openTestParticipateModal: 9637, 11922. closePledgeModal: 11917, 12000. 현재 같은 일반 스크립트의 뒤쪽 선언이 적용된다. 삭제·정리는 다음 단계에서 동작 검증과 함께 수행한다.
2. **일반 스크립트와 모듈이 함께 있음.** 큰 일반 스크립트는 5378–14693, 모듈 태그는 15109–15111(dataService → main → auth). 큰 스크립트를 바로 모듈로 바꾸면 인라인 핸들러와 전역 상태 연결이 달라진다.
3. **DOM 조회 시점이 중요함.** src/auth.js는 최상위에서 로그인 요소를 조회한다. 온보딩·약관 모달은 큰 스크립트 뒤에 있다. 분리 시 DOM이 준비되는 순서를 보존해야 한다.
4. **DOMContentLoaded 초기화가 두 곳에 있음.** 7983(썸네일), 14650(메뉴 이벤트·날짜·코인·알림·화면 복원·DB 초기화). 임의로 합치거나 실행 시점을 바꾸지 않는다.
5. **인증 코드도 DB 초기화를 호출함.** src/main.js는 데이터 서비스 등을 window에 연결하고, src/auth.js는 인증 흐름에서 initSupabaseLiveDB 등을 호출한다. 현재 호출 관계를 기록하고, 분리 후 중복 이벤트·조회·Realtime 구독 증가가 없는지 확인한다. 현재 중복 발생 여부를 실행으로 확인한 것은 아니다.
6. **공유 상태를 복제하지 않음.** currentViewKey/viewHistory(화면 이동), currentPostId(상세·참여·후기), userCoinBalance(지갑·상점·등록), currentParticipatingPostId(참여), isProjectEditMode/activeEditingProjectId(등록·수정), window.myProjectCollections 및 window.liveExploreProjects(조회 결과)의 소유 기능을 정한 뒤 이동한다.
7. **복원 동작을 보존함.** localStorage의 dondwae_current_view·dondwae_current_post_id, 알림 설정과 인증 관련 키, sessionStorage의 프로젝트 수정 대상·사용자별 미션 초안을 유지한다. 키 이름·저장 범위·만료 처리 변경은 파일 이동과 섞지 않는다.
8. **테스트가 소스 위치에 의존함.** 아래 15개 테스트 파일에서 index.html을 직접 참조한다. 마크업을 옮길 때 검사 대상을 조립 HTML이나 해당 모듈로 바꾸되, 검증 항목 자체를 삭제하지 않는다.

## 11. 사용자 직접 로그인 후 온보딩 확인

같은 날 사용자가 로컬 페이지에서 직접 로그인했다. 브라우저에서 계정 표시와 로그아웃 버튼, 온보딩 모달이 함께 나타나는 것을 확인했다. 이메일·입력된 개인 프로필 값은 이 문서에 기록하지 않는다.

- 실제 표시: `STEP 2 / 5`, “어떤 이름으로 활동하시겠어요?”
- 닉네임은 필수이며 최대 20자, 직업군·한줄소개는 선택 항목으로 표시됨
- 이전 버튼 비활성, 다음 버튼 활성
- 단계 표시에서 첫 단계에 체크 표시가 있었으나 약관 동의 절차를 직접 관찰한 것은 아님
- 온보딩 완료·DB 저장·새로고침 후 복원·완료 계정의 재로그인은 아직 미확인

모달은 사용자에게 넘겼으며 임의의 프로필을 입력하거나 동의를 대신 제출하지 않았다. 사용자 완료 후 이어서 확인한다.

## 13. 브라우저 확인에서 관찰한 기존 동작 문제

아래는 **파일 분리와 무관하게 이미 존재하던 문제**다. 9절 원칙대로 구조 변경과 섞지 않고 여기에만 기록한다. 이번 단계에서 고치지 않았다.

### 13-1. 프로필의 등록 자격 문구가 실제 게이팅 결과와 충돌한다

같은 계정, 같은 화면에서 프로필은 `피드백 3/3회 작성 완료! 내 바이브코딩 서비스 무료 등록 자격을 획득하셨습니다.`와 `다른 바이브코딩 프로젝트 피드백 3회 완료로 내 서비스 무료 등록 티켓 획득 완료!`를 보여주는데, `프로젝트 등록하기`를 누르면 `테스트 3회 이상 참여 필수 / 현재 다른 서비스 테스트 완료 횟수 0 / 3 회`로 차단된다. 근거는 25번 캡처다.

원인은 두 문구가 [creator-web/index.html](../creator-web/index.html)의 4457·4526줄에 **고정 텍스트로 박혀 있고 실제 자격 데이터와 연결되어 있지 않기** 때문이다. 게이팅 판정 쪽(projectGating)이 맞고 문구 쪽이 항상 완료 상태를 보여준다.

14절에서 자격을 실제로 갖춘 별도 계정(테스트 6회 완료)의 프로필을 확인한 결과 **같은 문구가 글자까지 동일하게** 나왔다(29번 캡처). 자격 유무와 무관하게 늘 같은 문장이 나온다는 뜻이므로, 이 문구는 자격 표시로 쓸 수 없다.

### 13-3. `view-notification-settings` 라우트에 진입 버튼이 없다

3절이 라우팅 화면 11개 중 하나로 센 화면인데, 현재 [creator-web/index.html](../creator-web/index.html)에는 `navigateTo('notification-settings')` 호출이 한 곳도 없다. 화면 정의(5242줄)와 제목 매핑(5441줄)만 남아 있다.

이전 배포 산출물 `creator-web/.vercel/output/static/index.html`의 5201줄에는 알림 목록 하단에 `일괄 수신 설정 편집` 버튼이 있었고 그것이 이 라우트로 들어가는 유일한 입구였다. 현재 index.html의 같은 자리에는 그 버튼이 없다. 화면 내용 자체도 `알림 수신 설정 (준비 중)` 안내판이다.

분리 시 이 화면을 **살아 있는 화면으로 취급할지 정리 대상으로 볼지 먼저 정해야 한다.** 그대로 옮기면 도달 불가능한 화면 파일이 하나 생긴다.

### 13-4. 모달이 Escape에 반응하지 않는다

테스트 참여 모달과 프로필 수정 모달 모두 Escape를 눌러도 닫히지 않았고, 각 모달의 `취소` 버튼으로만 닫혔다. 5절은 상단 메뉴의 `Escape·바깥 클릭` 처리를 보존 대상으로 적고 있지만, 모달에는 해당 처리가 없다. 분리 후 "원래 되던 것이 안 된다"고 오해하지 않도록 **현재 상태가 Escape 미지원**임을 기준으로 삼는다.

### 13-5. 상점 카테고리를 바꿔도 교환 패널의 선택 상품이 남는다

`프롬프트 템플릿`의 1,500 C 상품을 선택한 뒤 `노션 템플릿` 카테고리로 바꾸면, 목록에는 없는 그 상품이 교환 패널에 그대로 남는다(22번 캡처). `filterMarketCategory`와 `selectMarketProduct`가 선택 상태를 공유하지 않는다. 6절 6항의 "공유 상태 소유 기능을 정한다"에 이 조합을 포함해야 한다.

### 13-6. 등록 화면의 URL 검증이 사실상 빈 값만 거른다

`isValidCreateStepUrl`([creator-web/index.html](../creator-web/index.html) 7282줄)은 값에 `http(s)://`가 없으면 `https://`를 앞에 붙인 뒤 `new URL()`로 파싱한다. 그 결과 호스트명처럼 보이기만 하면 통과한다. 페이지에서 실제 함수를 호출해 확인한 결과다.

|---|---|
| `` (빈 값), 공백만 | 거부 |
| `http://` | 거부 |
| `javascript:alert(1)` | 거부 |
| `asdf` | **통과** |
| `...` / `!!!` | **통과** |
| `한글주소` | **통과** |

7절 B07의 "잘못된 URL" 항목은 **현재 구현에서는 빈 값 외에 재현되지 않는다.** 분리 후 이 함수를 옮길 때 동작이 같은지만 확인하고, 검증 강화는 별도 작업으로 다룬다.

### 13-7. 진입 경로에 따라 등록 서약을 건너뛴다

같은 이름의 `프로젝트 등록하기` 버튼이 화면마다 다른 함수를 호출한다. 페이지에서 각 화면의 버튼을 조회한 결과다.

| 화면 | 버튼 | onclick |
|---|---|---|
| 랜딩 | 프로젝트 등록하기 | `openPledgeModal()` |
| 탐색 | 프로젝트 등록하기 / 새 프로젝트 등록하기 | `openPledgeModal()` |
| 마이페이지 | + 프로젝트 등록하기 / 새 서비스 등록하기 | `navigateTo('create')` |

`navigateTo('create')`(11730줄)는 `window.userHasPassedGating`이 참이면 자격 검사도 서약 모달도 거치지 않고 바로 등록 화면으로 간다. 거짓일 때만 `ensureProjectGatingPassed()`를 거쳐 서약 모달의 차단 뷰를 띄운다.

따라서 **자격을 갖춘 사용자가 마이페이지에서 등록을 시작하면 서약 동의 화면을 한 번도 보지 않는다.** 탐색·랜딩에서 시작하면 서약 뷰(37번 캡처)가 표시된다. 이번 확인에서 두 경로를 모두 재현했다.

`pledge-modal`은 하나의 모달 안에 차단 뷰(`pledge-view-blocked`)와 서약 뷰(`pledge-view-allowed`)를 함께 갖고 있다. 4절이 `등록 서약·자격 안내`로 적은 것이 이 두 뷰다. 분리할 때 둘을 갈라 놓으면 `proceedPledgeModal`의 분기가 깨진다.
