## 진행 이유

기존 구현은 한 번의 사용자 행동을 여러 개의 독립 요청으로 처리했다.

- 참여 행 생성과 프로젝트 참여 인원 증가는 별도 요청이었다.
- 리뷰 화면은 DB 저장 성공을 기다리지 않고 브라우저 돼지코인을 먼저 올릴 수 있었다.
- 상점 교환은 교환 행 생성, 지갑 차감, 코인 원장 기록을 따로 처리했다.
- 브라우저에서 프로젝트 등록 자격(`has_passed_gating`)을 수정할 수 있었다.

따라서 중간 요청 하나만 실패해도 참여 인원, 리뷰, 지갑, 원장이 서로 달라질 수 있었다. 특히 돼지코인과 재고는 동시 요청에도 정확해야 하므로 서버의 단일 PostgreSQL 함수 안에서 잠금과 검증을 수행하도록 바꿔야 했다.

## 실DB 트랜잭션 검증

로그인 사용자 역할과 임시 프로젝트를 사용해 다음 흐름을 한 트랜잭션 안에서 확인했다.

1. 참여 RPC 실행 → 참여 1건, 프로젝트 `current_count` 1
2. 같은 프로젝트 재참여 → 중복 차단
3. 리뷰 RPC 실행 → 참여 상태 `submitted`, 리뷰 1건, 완료 횟수 1 증가
4. 프로젝트에 저장된 리워드 100돼지코인 지급 → 지갑 1,250에서 1,350
5. 가격 1,200돼지코인 상품 교환 → 지갑 150, 재고 100에서 99
6. 리뷰 리워드 원장 1건 및 상점 교환 원장 1건 생성
7. 참여·리뷰 직접 INSERT와 등록 자격 직접 UPDATE 모두 권한 오류로 차단
8. 전체 테스트 `ROLLBACK`

롤백 후 임시 프로젝트·참여·리뷰·교환·코인 거래는 모두 0건이며, 상품 재고는 100으로 복구됐다. 운영 사용자 지갑과 완료 횟수에도 테스트 변화가 남지 않았다.

## Advisor 결과

- 새 트랜잭션 RPC 3개와 기존 개인정보 RPC 2개는 의도적으로 `SECURITY DEFINER`를 사용하므로 경고 5건이 표시된다. 모든 함수는 로그인 역할에만 허용하고 `auth.uid()`를 서버에서 읽으며, 사용자 ID·리워드·가격을 입력받지 않는다. 비로그인 실행 차단과 직접 쓰기 차단을 역할 기반으로 검증했다.
- 유출 비밀번호 보호 기능 비활성 경고 1건은 기존 Auth 설정 항목으로 남아 있다.
- 이번에 추가한 인덱스는 운영 데이터가 아직 없어 미사용으로 표시된다. 즉시 삭제 대상이 아니다.
- 알림과 스크랩의 기존 미인덱스 외래 키 2건, 복구용 private 테이블의 기본 키 안내는 이번 거래 흐름과 별개인 후속 최적화 항목이다.

## 범위 밖 후속 작업

프로젝트 등록 시 예산을 결제하고 게시 상태를 바꾸는 흐름은 이번 단계에 포함하지 않았다. 참여·리뷰 보상·상점 교환은 완료됐으며, 실제 프로젝트 등록 비용을 운영할 때는 별도의 게시/예산 트랜잭션 RPC로 구현해야 한다.
